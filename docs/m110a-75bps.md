# MIL-STD-188-110A 75 bps (75S, 75L) and STANAG 4415

Requirement (Alex, 2026-11-24, from Steve AAM400): the appliance supports MIL-STD-188-110A and
STANAG 4415 at 75 bps, transmit and receive. This file says what was built, what the standards
say, what was measured, and what cannot be settled from the documents held.

Labels: **read** = read from a standard, a paper or code (cited); **measured** = measured with a
command named here; **inferred** = reasoning not yet measured; **secondary** = from a secondary
description, not the STANAG text. Section numbers are MIL-STD-188-110D's; 110C and 110C Change 1
carry the same 75 bps text word for word (read: `110c.txt` 1491, 1692-1713, 1843-1900; 110D
1272-1276, 1425-1446, 1573-1632).

## What the standard says (read)

| Item | 75 bps fixed frequency ("75N") | 110D |
|---|---|---|
| Coding | rate 1/2, K=7, no repetition: 150 bps coded | §5.3.2.3.3 b, Table V |
| Interleaver | 10 x 9 (short), 20 x 36 (long); load row + 7 modulo rows, fetch column - 7 | §5.3.2.3.4, §5.3.2.3.5, Table VI |
| Bits per channel symbol | 2 | Table VII |
| Modified Gray | 00, 01, 10, 11 -> 00, 01, 11, 10 | §5.3.2.3.6, Table IX |
| Symbol formation | each dibit -> 32 tribits, Table Xa; Table Xb for every 45th (short) / 360th (long) set after the sync | §5.3.2.3.7.1.1, Table X |
| Known symbols | none: S2 stays on UNKNOWN DATA | §5.3.2.2.2 b, Table XV |
| Scrambler | modulo-8 addition of the 160-periodic data sequence (BAD hex) | §5.3.2.3.8.1 |
| Preamble | 3 or 24 frames, D1,D2 = 7,5 (short) / 5,5 (long) | §5.3.2.3.7.2, Table XI |
| Message end | EOM 4B65A5B2 msb first, 144 flush bits, zeros to the block end | §5.3.2.3.1, §5.3.2.3.2 |
| Performance | 75 bps, 2 fading paths, 5 ms, 5 Hz, 2 dB SNR (3 kHz): BER 1e-5, long interleave | §5.3.2.5, Table XVI |
| Receiver | "shall use the modification of the known data at interleaver boundaries to synchronize without a preamble" | NOTE to §5.3.2.3.7.1.1 |
| Robust mode | "shall employ the waveform specified above for 75 bps operation, and shall meet the performance requirements of STANAG 4415" | §5.3.4; §5.3.1.3 f |

45 sets x 32 symbols = 1440 symbols, 9 scrambler periods; 360 sets = 72 periods. Every block
starts at scrambler offset 0 and its exceptional set sits at offset 128 (read, arithmetic).

Transmit (read, then measured by `test_m75`): bytes go LSB first, as in every other mode here.
The preamble is `BrainPreambleEncoder` with D1,D2 7,5 / 5,5; data symbols follow as one stream;
no probes. `test_m75` checks Tables IX and X against the standard's printed text, the interleaver
against a model written from §5.3.2.3.4/5, and the whole transmitted symbol stream (75S and 75L,
1 to 100 bytes) against a model written from §5.3.2 in the test file.

Receive (design; the standard leaves it open):

1. **Acquisition** (`m75_acq.h`). A preamble segment's 32 symbols depend only on its channel
   symbol (the sync scrambler restarts each segment), so the matched-filter output is correlated
   with the 8 segments once per half symbol, by descrambling and an 8-point Walsh transform. The
   13 segments other than D1/D2 are known once a frame's countdown is assumed. Each scores the
   share of its 8 word energies that falls on the expected word. The shares are summed over the
   last 3 or 24 frames before an assumed end of preamble (frames before the buffer are left
   out). Their excess over 1/8 each, in noise standard deviations (variance 7/576 per
   segment), is the significance z. z picks the end of preamble, the frame count and the
   carrier (7.5 Hz grid over +/-80 Hz, then 0.5 Hz). D1,D2 are read as a pair over those frames,
   from every defined code; the mode comes from the code, never from the metric. Found when z >= 9
   (measured: noise alone gave z up to 6.6 over 24 buffers of 20 s; 75S at -10 dB gave 15.9 or
   more, 75L at -15 dB 16.6 or more). Shares rather than raw energies, because with raw energies
   one segment landing on the preamble's first segment, with the rest in a quiet lead-in,
   outscored the true end. That happened on 75S at 40 Hz / 10 ms and +14 dB: the decode started a
   block early and passed the gate with 45 junk bits (measured, then fixed).
2. **Why not the shared acquisition** (measured): BrainDecoder needs a normalised correlation of
   one frame's 288 common symbols above 0.7 (`src/m110a/brain_decoder.h:544`) and ModemRX's
   AUTO pass 0.5 (`api/modem_rx.cpp`, "Mode detection failed"). That metric is at most
   sqrt(S/(S+N)): at -6 dB in 3 kHz it read 0.44, so neither opens much below 0 dB, while
   75 bps decodes to about -9 dB.
3. **Demodulation** (`m75_rx.h`). Per set, descramble and correlate with the four Walsh words of
   the set (normal or exceptional) at every tap of a +/-12 ms window, a quarter symbol apart.
   Each word's metric is its correlation energy summed over the taps, weighted by the mean
   power-delay profile less twice the noise floor: a non-coherent RAKE (square-law combining).
   The profile starts from the last preamble frame and follows the winning word (alpha 0.03); the
   noise floor follows the losing words; the window re-centres on the profile (clock drift).
4. **Decoding.** Max-log soft bits through Table IX, deinterleave by block, K=7 Viterbi. The
   message ends at the EOM. When the EOM took bit errors it is found by the clean flush after it:
   up to 3 errors with at most 8 ones in the 144 flush bits, or up to 6 with at most 4. Without
   an EOM the message is the whole blocks the signal covers.
5. **Gate.** The decoded bits are coded again and compared with the hard channel bits; p is the
   fraction that disagree, and quality_db = 10 log10((1-p)/p). Success needs quality_db >= 11.25
   dB and, on the worst interleaver block, the same measure >= 6.5 dB. Both thresholds were set on
   240 knee decodes (AWGN, CCIR moderate and poor, seeds 1-12): message-wide alone let 7 wrong
   decodes through, mostly 75S in fades longer than the 0.6 s interleaver; with the block term
   0 of 39 wrong and 123 of 192 right passed. Validated on seeds 13-24 (tables below). snr_db is
   estimated from the weighted metrics: (M_win - M_lose) / M_lose / (32 kappa).

ModemRX hands the 75 bps path its buffer from up to 5 s before its own preamble cut
(`m75::lead_in`): at low SNR `first_preamble_cut` fires inside a 75 bps preamble.

How far agreement is established: for the same payload bits, our 75S/75L transmission is,
symbol for symbol, the beginning of what MS-DMT's SYNC_EOM transmit would send (read, every step
above). The only difference is the end. After the EOM, MS-DMT feeds 32 more zero bits and then
a whole further block of zeros. Our last block holds the same zeros in the same places: once the
encoder has taken 6 zeros its output is zero. So MS-DMT sends at least one more all-zero block
after ours ends (inferred from the code read; not run). Our receiver never needs that block,
because it ends at the EOM. MS-DMT's receiver locates the exceptional set the same way
(`de110a.cpp:1282-1301`, counter reset at sync `rxm110a.cpp:2793`), which agrees with our
transmitter. **Measured the other way:** our receiver decodes MS-DMT's own 75S and 75L transmissions
(`release/examples/refrence_pcm/tx_75S_*.pcm`, `tx_75L_*.pcm`) exact, with the EOM (Measured,
below). **Not established:** MS-DMT decoding our audio. MS-DMT was not run. Playing
`m110a_tx --mode 75S/75L` output into MS-DMT would settle it.

## STANAG 4415 (secondary)

No copy of STANAG 4415 (Ed. 1, 24 Dec 1997, or AComP-4415) exists in the holdings searched
(coordinator's search: munin, uror groupsio, the mars-source-archive, saga's library). What can
be said:

- **Read, primary:** MIL-STD-188-110C/C CH1/D §5.3.4: the optional robust serial tone mode
  "shall employ the waveform specified above for 75 bps operation, and shall meet the
  performance requirements of STANAG 4415"; §5.3.1.3 f: "Robust 75 bps mode. If included, this
  mode shall be in accordance with STANAG 4415." STANAG 4539 Ed. 1 Annex B §2: the 75 bps
  "self-identifying waveform ... is fully specified in STANAG 4415. This waveform is required for
  75 bps operation for systems complying with this STANAG" (`4539Eed01.pdf`).
- **Secondary:** FFI report 2004/02015 "NATO Standards for HF Communications" §7: "The waveform
  of STANAG 4415 is the same as the 75 bps waveform of Mil-Std 188-110B, but the requirements of
  receiver performance in STANAG 4415 are stricter than those of 110B." It "works well with SNR
  values down to -7 dB, Doppler spread up to 40 Hz and multipath spread approaching 12 ms",
  created from the DAMSON high-latitude channel measurements. Otnes, dissertation (`CIR.pdf`)
  §2.3.3: "the two standards describe the same transmitted waveforms, but STANAG 4415 requires
  the receiver to perform well under more severe channel conditions". Johnson et al.,
  *Third-Generation and Wideband HF Radio Communications* (2013) §2: "The NBI performance
  specification of STANAG 4415 requires that the 75-bps waveform handle interferers at power
  levels ranging from 20 to 40 dB higher than the desired signal." Jorgenson and Moreland,
  "HF Serial-Tone Waveform Design" (CRC): "Both STANAG 4415 and Mil-Std 188-110A specify a 75
  bps in-band direct sequence spread spectrum modulation." MS-DMT v2.00 introduction: "Robust
  STANAG 4415 (S4415) performance at 75bps". MS-DMT's source has no 4415-specific code (grep).

So the 4415 waveform is the 75 bps waveform built here (primary: 110D §5.3.4 says the robust
mode uses it; secondary: every description says the same). What STANAG 4415 adds is receiver
performance, and that is NOT DETERMINABLE in its exact form (see below). What was measured
against the secondary figures is in the tables.

## NOT DETERMINABLE (and what would settle it)

- **STANAG 4415's performance requirements**: SNR/BER points, channel conditions, frequency offset
  and Doppler tolerances, acquisition time, interference tests. Only secondary figures are held:
  -7 dB, 40 Hz, 12 ms from FFI 2004/02015 (operating figures, not test points), and NBI of 20-40 dB
  above the signal from Johnson et al. The STANAG 4415 Ed. 1 text (NATO, 1997) or AComP-4415 would
  settle it.
- **Whether STANAG 4415 changes any bit of the waveform** from the 110 75 bps text. 110D §5.3.4
  makes a 110D robust mode use the 110 waveform. FFI and Otnes say the two waveforms are the
  same, and the 4539 Ed. 1 paper calls them "similar". Settled by the STANAG 4415 text.
- **Whether 4415 asks for synchronisation without a preamble.** 110D's NOTE to §5.3.2.3.7.1.1
  asks it of a 110 receiver ("shall use the modification of the known data at interleaver
  boundaries to synchronize without a preamble"). It is not built here (below). Settled by the
  4415 text for 4415; for 110 the requirement is read.
- **MS-DMT decoding our 75 bps audio**: agreement is by reading only (our receiver does decode
  MS-DMT's recordings). Running MS-DMT on `m110a_tx --mode 75S/75L` output would settle it.

## Not done, and what each would need

- **Late entry (synchronisation without a preamble)**, 110D NOTE to §5.3.2.3.7.1.1, read as a
  receiver requirement. What it would need (inferred): search for exceptional sets (Table Xb)
  at scrambler offset 128 over every half-symbol start, 0.6 s apart for 75S and 4.8 s apart for
  75L. That gives the block boundary, and with it the interleaver, the scrambler phase and the
  mode, because a block always starts at scrambler offset 0.
- **Narrowband interference excision** (secondary: 4415 asks 20-40 dB). Measured: a CW tone at
  1500 Hz 10 dB or 20 dB above a 75S signal at 0 dB SNR defeats acquisition and decode
  (success=0, no false success). A tone of the signal's power (0 dB SIR) or 10 dB below it does not.
- **m110a_rx's preamble scan** (`m110a_rx/main.cpp`, threshold 0.45, PreambleCorrelator over one
  frame) finds no 110A preamble below about -7 dB in 3 kHz. So through m110a_rx a 75 bps message
  decodes only to about -6 dB, while ModemRX decodes it to -9 dB. Measured: at -9 dB m110a_rx
  reported "0 preamble(s) found". At `--threshold 0.3` it found the preamble, but a false second
  hit cut the window. The fix belongs in m110a_rx: a 75 bps-aware scan, for example
  `m75::acquire`. That file is another branch's (fix/m110a-quality-gate), so it is left alone.
- **Streaming (`push_samples`) at low SNR**: `decode_internal` sends a preamble already read as
  75 bps to `m75::decode`. It does not try `m75::find_low_snr` when the shared detection fails.

## m110_lan (110D Appendix A) and 75 bps, the later step

What it will need (read from `m110_lan/main.cpp`; nothing changed there):

- 75S/75L in `kModes` (main.cpp:93-99). The comment there, its usage text (main.cpp:1608) and
  `docs/110d-appa-lan.md:242` still say 75 bps has no data path.
- Blocking factor: `blocking_factor()` gives rate x span = 45 bits (75S) and 360 bits (75L)
  (main.cpp:101-105). 45 bits is not a whole byte. How Appendix A carries a blocking factor
  that is not a byte multiple has to be read in A.5.1.1.8/9 before 75S goes on the wire.
- Burst detection: `read_mode` needs the PreambleCorrelator over 0.45 and a 2:1 D1/D2 lead over
  at most 3 frames (main.cpp:1375-1400). Like m110a_rx, that stops near -6 dB. `m75::acquire`
  reads D1/D2 over the whole preamble.
- Burst end by level (the geometric mean of signal and noise): at negative SNR the level hardly
  changes. The 75 bps path should end at the EOM, or at the last block with signal
  (`RxOut::signal_sets`).
- Latency: a 75L block is 4.8 s. Data can go to the DTE block by block as each block decodes.
- FEC for the LAN packets: Table A-XVII gives (6,2) for rates up to 2400. 75 bps falls in that row.
